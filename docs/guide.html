1 · איך עובד ה‑UI

הרעיון בגדול

יש ליבה שיודעת את חוקי המשחק ומצב הלוח (לא יודעת כלום על מסך), ויש שכבת UI שלוקחת "צילום מצב" מהליבה ומציירת אותו. הקלט (עכבר) הולך בכיוון ההפוך: מהמסך אל הליבה. שתי השכבות מדברות רק דרך שני דברים: פקודות (מהלך/קפיצה) ו‑RenderModel (צילום‑מצב לתצוגה).

מה קורה כשמריצים python play.py

  1. נבנה מנוע המשחק (GameEngine) עם הלוח שנטען מ‑assets/board.csv.
  2. נטענים כל ה‑sprites (תמונות הכלים) מ‑assets/pieces/ לזיכרון.
  3. נפתח חלון, ומתחילה לולאת המשחק שרצה שוב ושוב עד שסוגרים.

מה קורה בכל סיבוב של הלולאה (פריים)

1 · dt = כמה זמן עבר מהפריים הקודם (בשעון אמיתי)
2 · engine.wait(dt) — מקדמים את השעון של המשחק ב‑dt
3 · model = engine.render_model() — מבקשים צילום‑מצב עדכני
4 · הרנדרר מצייר: לוח → כלים → הדגשות
5 · ה‑HUD מצייר: ניקוד, זמן, באנר
6 · מציגים את התמונה בחלון
7 · קוראים לחיצות עכבר ומעבירים אותן לליבה

הנקודה החשובה: הזמן לא נקרא בתוך הליבה — הלולאה מודדת אותו בחוץ ומזריקה אותו פנימה (wait(dt)). זה מה שיאפשר בעתיד לשים שרת שמנהל את הזמן במקום הלולאה.

מה קורה כשלוחצים

  • קליק שמאלי על כלי → נבחר (מודגש בירוק).
  • קליק שמאלי על יעד → הליבה בודקת חוקיות; אם חוקי, הכלי מתחיל להחליק ליעד.
  • קליק ימני → הכלי קופץ במקום (יירוט תוקף).

הזרימה: החלון תופס את הלחיצה (בפיקסלים) → InputTranslator מעביר ל‑Controller → ה‑Controller מתרגם פיקסל לתא ומבקש מהליבה מהלך/קפיצה.

איך עובדת האנימציה

אנימציה היא רצף תמונות‑נייח (פריימים) שמוצגות במהירות, כמו ספר‑זבוב. לכל מצב של כל כלי יש 5 פריימים (1.png…5.png). קובץ config.json ליד כל מצב אומר כמה פריימים בשנייה ואם האנימציה חוזרת בלולאה. ה‑renderer מחשב "איזה פריים להציג עכשיו" לפי השעון, ומצייר אותו.

אם ראית פעם מספרים 1→5 מתחלפים על הכלים — אלה היו תמונות ה‑placeholder (pieces1), שעליהן צויר מספר‑הפריים. עכשיו משתמשים ב‑pieces2 (ציור אמיתי), אז רואים אנימציה אמיתית במקום מספרים.

מצבי הכלי (מכונת מצבים)

  • idle עומד. אנימציה שחוזרת בלולאה.
  • move מחליק ליעד (מצייר בין התאים לפי אחוז ההתקדמות).
  • jump קופץ במקום.
  • long_rest / short_rest מנוחה (cooldown) אחרי מהלך/קפיצה. הכלי לא יכול לזוז עד שהמנוחה נגמרת, ומסומן בכיסוי אדום.

המעברים: מהלך→long_rest→idle, קפיצה→short_rest→idle. הם נקבעים ע"י ה‑config.json של הנכסים, לא מקודדים קשיח.

ה‑HUD והציור

מתחת ללוח יש רצועה שמראה כמה כלים נשארו לכל צד, הזמן שחלף, ובאנר "GAME OVER" כשמלך נלכד. כל ציור על המסך עובר דרך מחלקת Img (עוטפת OpenCV); רק שתי מחלקות נוגעות ב‑OpenCV: Img (ציור) ו‑Window (חלון + קלט).

2 · ארכיטקטורה

מפת השכבות

  img.py                 # Img מיובא מ‑CTD26 (פרימיטיב הציור). לא שונה
  window.py              # Window: חלון cv2 + קלט
  assets.py              # read_image, AssetLoader, solid, white→alpha
  sprite.py / sprite_library.py  # אנימציה + חיפוש לפי token+state

ui/                      # תצוגה/קלט — בלי cv2, בלי engine
  graphics_renderer.py   # RenderModel → canvas דרך Img
  hud.py                 # score / זמן / באנר game‑over
  input_source.py        # אירוע‑מכשיר → פקודת Controller

gateway/
  gateway.py             # GameGateway (Protocol) + NetworkGateway (עתיד)

view/
  render_model.py        # RenderModel / RenderPiece — DTO קפוא
  snapshot.py, renderer.py  # המודל/רנדרר הטקסטואלי (VPL) — לא שונה

play.py                  # כניסה גרפית + composition root + הלולאה
assets/                  # board.png, board.csv, pieces/

התפרים המרכזיים

  1. GameGateway — חוזה בלבד. ה‑UI תלוי ב‑Protocol הזה, לא ב‑GameEngine הקונקרטי. ה‑engine מקיים אותו ישירות, אז אין מחלקה כפולה. זה התפר שיאפשר רשת בעתיד בלי לגעת ב‑UI.
  2. RenderModel — DTO קפוא. מה שעובר לתצוגה הוא read‑model בלתי‑משתנה. לא מדליפים Board חי — בדיוק מה ששרת סמכותי היה שולח ללקוח דק.
  3. cv2 מבודד לשתי מחלקות בלבד (Img, Window). כל השאר נקי מ‑cv2. ציור = רק דרך Img.
  4. הזמן מוזרק (dt). הליבה עיוורת‑לשעון; זה מה שיאפשר שרת שמחזיק את השעון הסמכותי ומסדר מהלכים מתנגשים לפי timestamp.

פורמט tokens והתרגום

הליבה משתמשת בפורמט <צבע-קטן><סוג-גדול> (wP, bK). נכסי CTD26 משתמשים ב‑<סוג><צבע> גדול (PW, KB). התרגום 1:1 קורה רק בשתי נקודות‑מתאם: load_csv_board (קלט) ו‑SpriteLibrary (חיפוש sprite). הליבה לא רואה לעולם את הפורמט החיצוני.

איך מרחיבים בהמשך

  • רשת / שרת‑לקוח: לממש את NetworkGateway — אותן חמש מתודות מעל רשת, מול engine בשרת. ה‑UI לא משתנה.
  • ריבוי שחקנים: מקור‑קלט = InputTranslator אחד עם Controller משלו. שחקן שני = זוג נוסף. ה‑engine כבר תומך ב‑ALLOW_CONCURRENT_MOVES.
  • פיצ'רים בתצוגה נוספים ב‑ui//graphics/ בלבד; פיצ'רים בחוקים ב‑rules/ דרך ה‑registry.
בדיקות: הלוגיקה כולה מכוסה ב‑100%. המעטפת הגרפית (Window, לולאת play.run) מסומנת pragma: no cover, ו‑Img המיובא מוחרג ככוד צד‑שלישי.
